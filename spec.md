# WiCER Reproduction Spec

Reproducing *WiCER: Wiki-memory Compile, Evaluate, Refine* (arXiv:2605.07068v1).

## 0. Scope

Three experiments, in dependency order:

1. **E1 — Full-context (FC) KV cache vs. RAG on curated knowledge** (Policygenius, 30 docs). Expect FC to win: 4.38 vs. 4.08 quality, 7.3× faster TTFT.
2. **E2 — Scalability gap** (RepLiQA, 17 topics × 80 docs). Expect the reversal: FC 3.46/3.47 vs. RAG 3.63.
3. **E3 — Compilation gap + WiCER** (same corpus). Blind compilation collapses to 2.14–2.32; WiCER recovers to ~3.18–3.24, catastrophic failures 55.1% → 24.8%.

E2 is the load-bearing one — E3 has no meaning without its FC-raw baselines. E1 is optional (different corpus, needs scraping) and can be skipped if time is short.

## 1. Two machines / two budgets

| Role | What | Cost driver |
|---|---|---|
| **Reader** (inference under test) | Llama 3.1 8B Instruct, GGUF, served by `llama-server` from llama.cpp | GPU rental hours |
| **Compiler / judge / QA-gen** | Claude Sonnet via Anthropic API | API tokens |

The reader must be a *cached-prefix* server — the whole result is about warm KV cache TTFT. Use `llama.cpp` with prompt caching, not vLLM, unless you re-verify that cache reuse actually engages.

**GPU sizing:** RTX 4090-class (24 GB) is sufficient and is what the paper projects to (Appendix D). Llama 3.1 8B Q5_K_M is ~5 GB, leaving ~19 GB for a 96K-token KV cache. Do **not** use Q4 KV cache as the headline config on CUDA — the paper found Q4 KV degrades quality at 80 docs (Q8 wins 13/14 topics); use **Q8 KV**, which is free of penalty on CUDA.

**Budget estimate:** ~$1–2 API per WiCER iteration per topic (~130K input + ~17K output tokens), ~50 min wall clock. 17 topics × ~2 iterations ≈ **$40–70 API**. GPU: ~2–3 h per topic for FC + RAG + eval ≈ **40–50 GPU-hours** for the full 17-topic sweep. Pilot on 3 topics first.

## 2. Fixed configuration

Reader:
- Model: `Llama-3.1-8B-Instruct`, `Q5_K_M` GGUF
- Context window: **96K** tokens
- KV cache: **q8_0** (run a Q4 arm only for the ablation)
- Flash Attention on, greedy decoding (`temperature=0`)
- One preflight request per corpus to prime the cache; subsequent queries send only the ~30–50 token question suffix

RAG baseline:
- Chunks: 1,800 characters, 360-character overlap
- Embeddings: `all-MiniLM-L6-v2`
- Retrieval: top-5 by cosine similarity, no reranking
- Same chat template as FC

Judge (Anthropic API):
- Claude Sonnet, 1–5 rubric, identical for every condition
- System prompt verbatim from Appendix B:
  > You are an expert evaluator comparing a generated answer against a gold-standard answer. Score the generated answer from 1 to 5: 5 = Perfect -- captures all key facts, accurate; 4 = Good -- mostly correct, minor omissions; 3 = Acceptable -- partially correct, misses details; 2 = Poor -- significant errors or major omissions; 1 = Wrong -- incorrect, irrelevant, misses the point. Respond ONLY with valid JSON: {"score": <1-5>, "reasoning": "<explanation>"}
- Score 1 = "catastrophic failure"; this rate is a headline metric, track it separately from the mean

## 3. Data

**RepLiQA** (Montero et al., NeurIPS 2024 D&B; CC-BY-4.0) — the primary corpus. Public on HuggingFace. Use 17 topic domains × 80 documents × 400 QA pairs = 6,800 questions. Per-topic corpora run 55K–95K tokens.

Note: two topics (`regional_cuisine`, `regional_folklore`) exceed the 96K window at 80 docs (~97.2K tokens) and have **no FC baseline** — they run under RAG and wiki conditions only. Expect 15 usable FC topics, 17 for everything else.

**Policygenius** (E1 only) — 30 public web articles, ~67K tokens, ~2,250 tokens/article. Not redistributed by the authors; scrape or substitute any curated ~30-article corpus of similar size. QA: 240 pairs generated by Claude Sonnet (5–10 per article: factual, definitional, comparative, practical), each answerable only from its source article and tagged with the source filename.

## 4. Metrics

Per question: TTFT, total response time, generation throughput (via streaming SSE), judge score. For RAG additionally: retrieval accuracy (is the source article in the top-5, and at what rank).

Aggregate per topic: mean score, % ≥ 4, % = 1, median/P5/P95 TTFT, median throughput.

## 5. WiCER algorithm (E3, the actual contribution)

Input: documents `D = {d_1..d_N}`, target compression ratio `r`, max iterations `T` (use `r = 0.50` "moderate", `T = 3`).

```
Q_probe ← one QA pair per source document          (80 probes/topic)
W_0     ← Compile(D, r)                            # blind compilation
F_cum   ← {}
for t in 0..T-1:
    answers ← generate each q in Q_probe against W_t   # local reader, free
    Failures_t ← { q : judge_score(q) ≤ 1 }
    if |Failures_t| == 0 or (t > 0 and improvement < 10%): break
    for q in Failures_t:
        F_cum ∪= extract_critical_facts(source_doc(q))   # ~50–100 words each
    W_{t+1} ← Compile(D, r, preserve = F_cum)
return best W_t
```

Implementation notes that matter:
- **Probe selection**: exactly one QA pair per source document, so coverage is uniform; the remaining ~320 pairs/topic are the held-out eval set.
- **Diagnosis is targeted, not generic.** Extract the specific facts the dropped answer needed, ~50–100 words per failure, versus ~700 words per source document. This is the whole result: the ablation shows random pinning of an equivalent-length passage buys +0.16 while diagnosed pinning buys +0.95.
- **Preservation is a hard constraint** in the next compile prompt: pinned facts go in verbatim, and the compiler must include them *before* allocating budget to general coverage.
- The compiler is blind to the eval questions.
- Expect convergence at iteration 1–2. Ten of 17 topics peak at iteration 2. Don't run more — "random knowledge displacement" (pinning crowds out other content) causes a plateau, not monotone gain.

**Compiler compression is not obeyed.** Targets 75/50/25% yield actual 35.4/12.2/8.2%. Measure and report actual ratios; do not assume the target held. If you fix the compiler to hit its targets, you have changed the experiment — report it as a deviation.

## 6. Conditions to run

| Condition | Corpus per query | Needed for |
|---|---|---|
| FC raw (80 docs) | full topic corpus | E2, E3 baseline |
| RAG top-5 | ~2K tokens | E2, E3 |
| Wiki-blind, light / moderate / aggressive | compiled | E3 |
| WiCER iter 1, iter 2 | compiled + pinned | E3 |
| Random-pin control | compiled + random passages | E3 ablation |
| FC Q4 KV vs. Q8 KV | full corpus | quantization ablation |

The random-pin control matters: it is the only thing separating "diagnosis works" from "pinning anything works." Match every parameter to WiCER except the choice of pinned text; use an independent blind compilation per topic.

## 8. Success criteria

Reproduction succeeds if, across 17 RepLiQA topics:

- FC raw mean ≈ 3.46–3.47, RAG mean ≈ 3.63–3.64 (RAG wins by ~0.17)
- Blind moderate compilation ≈ 2.25, score-1 rate 53–60%
- Best WiCER ≈ 3.18 over 17 topics / ≈ 3.24 over the 15 with FC baselines, score-1 rate ≈ 24.8%
- Recovery ≈ 80% of the blind-compilation quality gap; catastrophic failures down ~55% relative
- Ablation: random pinning ≈ +0.16 over blind, WiCER ≈ +0.95

Directional agreement (the crossover exists, targeted diagnosis beats random pinning by a wide margin) is the real bar. Exact numbers will move — the compiler is stochastic and on different hardware TTFT changes outright.

## 9. Known reproduction risks

- **Single seed, no error bars.** The paper reports no confidence intervals; greedy decoding makes within-topic variance zero but compiler non-determinism means blind baselines differ between the paper's own Tables 4 and 5. Run ≥3 seeds of the compiler if budget allows — this is the cheapest improvement over the original.
- **Judge drift.** Claude Sonnet version is unpinned in the paper. Pin an exact model ID and record it; judge scores are the dependent variable in every table.
- **Hardware.** The paper runs on Apple M4 Pro / Metal. On CUDA, Q4 KV has no penalty and TTFT drops to ~0.2 s, so quantization and latency conclusions will differ legitimately. Quality conclusions should hold.
- **`local_education_systems`** shows 0% WiCER recovery in the original. If it fails for you too, that is a reproduction, not a bug.
- One topic in five conditions was human-validated (n=100, Pearson r=0.94 vs. judge). Consider a small human spot-check before trusting a divergent result.
